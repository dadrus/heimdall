Main

The main service evaluates incoming HTTP requests against configured access-control rules. In decision mode, it returns an authorization result to an integrating proxy or API gateway. In proxy mode, it forwards authorized requests to an upstream service.

For available configuration options see main port.

Main Service

This reference entry describes the request data used for access-control evaluation and the possible responses. See Rules for details of request matching.

Process an HTTP request

GET /{path_and_query_params}

This operation represents heimdall’s main HTTP request interface. It is not limited to GET. All other HTTP verbs are also supported and are subject to the configured rules. Method-specific HTTP semantics still apply: HEAD responses have no body, and configured CORS preflight OPTIONS requests can be handled without rule evaluation.

Requests may have nested paths and query strings. The path placeholder shown above is illustrative: it does not express a single-segment restriction on the requests that heimdall can process.

Response statuses and bodies depend on the matching rule and operating mode. In proxy mode, the upstream service determines the response, so its status codes are not limited to the examples listed below.

X-Forwarded-* and Forwarded headers are trusted only when the sender matches the configured trusted_proxies. Additional application-specific headers and cookies can be evaluated by the configured rules.

Parameters

  • path_and_query_params: string (path, required)

    Actual requested path, including any nested segments and optional query string, to be evaluated against the configured rules.

  • X-Forwarded-Method: string (header, optional)

    HTTP method to use for rule evaluation. Defaults to the method of the request received by heimdall when this header is absent.

  • X-Forwarded-Proto: string (header, optional)

    HTTP scheme to use when evaluating the request URL. When absent, heimdall uses the scheme of the incoming request.

  • X-Forwarded-Host: string (header, optional)

    Original request host to use when evaluating the request URL.

  • X-Forwarded-Uri: string (header, optional)

    Original request path and query string to use for rule evaluation.

  • X-Forwarded-For: string (header, optional)

    Client IP address information supplied by a trusted proxy.

  • Forwarded: string (header, optional)

    Standardized information about the original request and its proxy forwarding chain.

  • <Application Specific>: string (header, optional)

    Placeholder for other headers, the defined rules make use of.

  • <Application Specific>: string (cookie, optional)

    Placeholder for cookies, the defined rules make use of.

Responses

  • 200: A successful decision normally returns HTTP 200 in decision mode, unless a different status is configured. In proxy mode, an authorized request is forwarded and the upstream service determines the response status and body; HTTP 200 is only one possible result.

  • 400: Bad Request. Returned if the evaluated request path contains dot segments (. or ..), including URL-encoded variants (case-insensitive), e.g. %2e, %2f, and %5c combinations, to prevent path traversal.

  • 401: Unauthorized. Returned if a matching rule could not verify the authentication status of the subject related to the request.

  • 403: Forbidden. Returned if a matching rule could not verify the authorization status of the subject related to the request.

  • 404: Not Found. Returned if there was no rule found, which could be used to verify the request.

  • 405: Method Not Allowed. Returned if the matched rule does not permit the HTTP method.

  • 500: Internal Server Error. Returned when the service cannot process the request because of an internal error.

  • 502: Bad Gateway. Returned if communication with an upstream service fails, for example because of DNS or timeout errors.
